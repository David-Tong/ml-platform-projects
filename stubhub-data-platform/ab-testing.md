# StubHub A/B 测试：新模型上线后是否真的有效

## 1. A/B Testing 是什么

机器学习里的 A/B Testing 不是训练算法，而是通过随机对照实验，评估模型或产品策略上线后是否改善用户体验和业务结果的方法。

离线评估回答“模型在历史样本上预测得怎样”；A/B 测试回答“让用户实际使用新方案，相比旧方案，业务指标会发生什么变化”。不能仅凭 AUC、NDCG 或 RMSE 改善，就认定新模型应该全量上线。

本文以推荐系统解释完整实验，再说明卖家定价建议如何实验。算法、指标和数值均为示例，不代表已经核实的 StubHub 生产配置。

## 2. 一个具体例子：旧推荐模型与新推荐模型

假设线上方案 A 是现有召回与排序，新方案 B 更换了排序模型：

```text
A 组：现有召回 → XGBoost Rank V1 → 展示活动列表
B 组：相同召回 → XGBoost Rank V2 → 展示活动列表
```

保持召回和界面一致，有助于把差异归因到排序版本。如果 B 同时改成 ALS 召回与新的深度排序模型，也可以实验，但结论是“整套推荐方案”的效果，不能单独归因于排序算法。

例如，旧模型离线 AUC 为 0.77，新模型为 0.81。新模型仍可能因推荐过于集中、候选覆盖下降或响应变慢而导致购买转化下降。A/B 测试要检验的是实际业务结果，而不是再次验证离线 AUC。

启动前写下假设，例如：**在符合条件的推荐用户中，新排序提高分组后 7 天的购买用户比例，同时不使延迟、退款和用户体验超过预设退化界限。** 主指标、窗口、样本量、实验周期和发布门槛应提前确定。

## 3. 用户怎样分到 A、B 两组

### 3.1 稳定随机分桶

对于希望用户体验持续一致的推荐实验，通常按稳定用户标识分组。下面是伪代码：

```python
bucket = stable_hash(experiment_id, user_id, salt) % 10000
variant = 'A' if bucket < 5000 else 'B'
```

符合条件的用户约 50% 进入 A、50% 进入 B。同一实验内，在身份和分流配置不变时，同一用户保持同组。不同服务使用相同的编码、哈希算法和实验配置；不能直接依赖可能随进程变化的语言内置 `hash()`。

实验还要定义匿名用户登录后的身份衔接、跨设备规则，以及用户何时首次满足入组条件。不能将付费用户全部放 B、普通用户全部放 A，再把差异当作模型效果。

### 3.2 为什么不每次请求重新随机

如果同一用户第一次看到 A、第二次看到 B，收藏、搜索和购买行为就可能受到两种方案共同影响，难以估计持续使用某种推荐的效果。因此本文采用用户级分组。

请求级随机不是永远错误，但它回答不同问题，且需要处理用户内相关性和跨请求影响。选择用户、会话、卖家或市场作为随机单位，应由产品作用范围和相互影响决定。

### 3.3 分配不等于曝光

**分配是“决定给用户哪套方案”，曝光是“这套方案的内容实际展示出来”。** 两者发生在不同步骤：

```text
用户进入预先定义的实验入口
    → 分流服务将用户分配到 B 组：记录分配日志
    → 调用 B 模型生成推荐
    → 推荐结果返回页面
    → 推荐卡片满足预定义展示条件：记录曝光日志
    → 用户可能点击，也可能不点击
    → 用户可能购买，也可能不购买
```

例如曝光条件可以是卡片进入可视区域并达到约定时长；具体条件由产品提前统一定义。模型生成了推荐，不代表页面收到结果；页面收到结果，也不代表用户滚动到了该区域。曝光日志表示满足可观测的展示条件，不保证用户真正注意到了内容。

| 用户情况 | 是否已分配 | 是否发生新模型曝光 | 主分析怎样处理 |
|---|---|---|---|
| 分到 B，成功看到推荐，但没有点击 | 是 | 是 | 保留在 B，点击记为未发生 |
| 分到 B，页面在展示前被关闭 | 是 | 否 | 仍保留在 B |
| 分到 B，新模型超时，降级到旧模型 | 是 | 否；另记实际使用的旧版本 | 仍按原始分配保留在 B，不能改算进 A |
| 分到 B，看到推荐并购买 | 是 | 是 | 保留在 B，按统一结果口径记录购买 |

**为什么不能只比较“成功曝光的人”？因为是否曝光本身可能受新模型影响。** 假设 A、B 各随机分配了 1,000 人：

| 组别 | 分配人数 | 成功曝光人数 | 购买人数 |
|---|---|---|---|
| A | 1,000 | 900 | 90 |
| B | 1,000 | 600 | 72 |

假设这里的购买都发生在曝光用户中，且观察窗口完整。只看成功曝光的人，A 的购买比例是 `90 / 900 = 10%`，B 是 `72 / 600 = 12%`，似乎 B 更好。但按全部入组用户比较，A 是 `90 / 1,000 = 9%`，B 是 `72 / 1,000 = 7.2%`。如果 B 因为更慢而让更多用户等不到展示，它造成的损失也是上线效果的一部分，不能把这些用户从分析中删掉。

因此，本文主要比较**原始分配到 A、B 的合格入组用户**，这种思路称为按分配分析（intention-to-treat，ITT）。它回答：“把目标用户交给 B 方案，包括其超时和降级，会比交给 A 好多少？”未点击、未购买的用户保留在分母中；降级用户按原组统计，同时单独监控降级率。未购买必须是在结果数据完整、观察窗口成熟后确认，缺失日志不能直接当作没有购买。

**如果大量入组用户根本不会进入推荐页面，能不能缩小范围？可以，但要选对触发点。** 例如提前规定：只有用户进入推荐页面、页面准备请求推荐时才入组，再随机决定调用 A 还是 B。这样可以研究真正进入该场景的用户，同时保留分组后超时、关闭页面和未点击的用户。

若用户早已分组，也可以在两组采用同一套、发生在模型调用前且不受实验影响的场景触发条件，开展预先约定的触发分析。它回答的是“对进入该场景的用户有什么效果”，而非所有 App 用户的效果。若是否进入场景已受到此前 A/B 体验影响，则不能直接认为筛选后的两组仍然可比。

成功展示、点击和购买都是模型调用后的结果，不能用它们筛选主要比较人群。按曝光或点击计算的 CTR、漏斗等仍可作为分析指标，但不能因此将未曝光或未点击用户从购买转化等用户级主分析中移除。

## 4. 实验看哪些指标

| 指标 | 示例定义 | 用途 |
|---|---|---|
| 购买用户转化率 | 分组后 7 天内至少购买一次的用户数 / 入组用户数 | 可作为推荐实验主指标 |
| 每用户净收入 | 规定窗口内平台净收入总额 / 入组用户数 | 衡量商业价值，需区分平台收入与成交总额 |
| CTR | 点击次数 / 有效曝光次数 | 观察互动，不直接等于购买或收入改善 |
| 留存率 | 入组用户在预定义日期或窗口再次使用产品的比例 | 观察长期体验，需等待窗口成熟 |
| 护栏 | 错误率、延迟、退款取消、投诉等 | 限制用户或业务损害 |

每个指标都要明确分子、分母、去重、窗口、币种及退款规则。主指标宜提前确定，其他指标用于解释和护栏，不能事后挑显著的一项宣称成功。护栏“不显著变差”不等于已证明安全，应按预定义的可接受退化界限评估。

CTR 上升也可能来自更吸引点击但不促成购买的内容；CTR 下降而购买或长期价值改善时，也不能机械淘汰模型。决策依据是预先约定的目标和业务权衡。

## 5. 怎样判断差异是真效果还是随机波动

### 5.1 一个可计算的例子

假设用户级随机，每位用户都已完成 7 天观察窗口：

| 组别 | 入组用户 | 购买用户 | 购买转化率 |
|---|---|---|---|
| A | 100,000 | 10,000 | 10.0% |
| B | 100,000 | 10,300 | 10.3% |

绝对提升为 **0.3 个百分点**，相对提升为 **3%**。不能只因 B 更高就上线，还要估计不确定性。

在两组用户独立、每用户一个购买指示变量等假设下，大样本两比例检验的双侧 p 值约为 0.026；差值的正态近似 95% 置信区间约为 **0.035 到 0.565 个百分点**。这些是示例计算，不是实际实验结果。

p 值表示在零差异假设下，观察到当前或更极端统计结果的概率，不是“B 没有效果的概率”。统计显著也不等于收益足以覆盖服务成本，仍需看效应大小、置信区间和护栏。

### 5.2 检验方法怎样选

| 指标 / 数据结构 | 可考虑的方法 | 关键限制 |
|---|---|---|
| 每用户是否购买 | 大样本两比例 z 检验；稀疏数据可用精确方法 | 分析单位与随机单位一致 |
| 每用户收入等均值 | Welch t 检验或合适的重采样方法 | 关注长尾、极端值及用户内相关性 |
| CTR 等比率指标 | 用户级聚合后采用 delta method 或按随机单位 bootstrap | 不能把同一用户的多次曝光当独立用户 |
| 分组人数是否符合分流比例 | 卡方拟合优度等 SRM 检查 | 检查的是实验质量，不是业务收益 |

检验应匹配随机化和指标结构，不能把 t-test、z-test、卡方当成任意互换的按钮。多个变体、多个正式检验或大量切片，需要预定义多重比较处理；切片探索不能直接等同于已验证结论。

### 5.3 样本量、实验周期和停止规则

实验前用历史基线、最小可检测效果（MDE）、显著性水平、统计功效及分流比例规划样本量。MDE 是希望有能力检测的效果尺度，不自动等于上线门槛。

例如基线转化约 10%，希望检测绝对 0.3 个百分点变化，双侧显著性水平 5%、功效 80%、等比例分组时，常规独立比例近似需要每组约 16 万用户。实际需结合失访、聚类、窗口成熟和分流情况重新计算；上面的每组 10 万结果显著，并不与规划功效不同相矛盾。

实验既要达到计划样本量，也要覆盖相关业务周期，并等待最后入组用户的观察窗口成熟。固定样本检验不能每天查看 p 值并在首次小于 0.05 时宣布成功；需要持续正式决策时，应事先采用合适的序贯设计。严重故障和护栏风险可以按预设安全规则停止。

## 6. 新模型从训练到上线的完整过程

1. **离线训练与评估**：训练 ALS、XGBoost 或其他候选，检查数据泄漏、AUC、NDCG 等和关键切片。未达到预设候选门槛则修正；探索性实验需要另外说明理由。
2. **Shadow 测试**：线上请求同时供候选模型预测，但用户仍使用旧结果。检查输入、输出、延迟和资源；shadow 没有用户接受新结果，不能据此证明业务提升。
3. **A/A 与分流校验**：必要时两组都运行相同方案，检查身份、稳定分桶、指标链路及 SRM。A/A 不保证未来实验必然正确。
4. **小流量安全验证**：向少量用户开放 B，检查错误、延迟和严重业务风险。低流量阶段通常没有足够功效判断业务优劣。
5. **正式 A/B 实验**：按预设比例、样本量、周期和停止规则比较主指标与护栏。
6. **决策与放量**：通过数据质量、业务和统计门槛后逐步扩大范围，持续监控并保留回滚；结果不确定则按计划结束或开展新实验，不随意延长直到显著。

1% → 5% → 10% → 50% → 100% 可以作为发布示例，不是必须顺序。改变分流比例要保留原用户分配，记录时间段并按预先设计分析，不能随意汇总所有阶段。模型 Endpoint 的随机流量切分也不自动等于稳定用户级实验，应由业务实验分流控制用户路由。

## 7. StubHub 卖家定价建议怎样做实验

价格预测系统的产品目标是：**卖家列票时给出建议价格范围，并说明预计多快可以成交。** 可以比较旧建议策略 A 与新建议策略 B，而不是只比较两模型的成交价 RMSE。

| 设计项 | 示例 |
|---|---|
| 处理差异 | A 展示旧版价格范围与成交速度建议；B 展示新版建议 |
| 随机单位 | 优先考虑卖家级稳定分组，避免同卖家不同挂牌反复看到不同策略；最终依产品与干扰评估确定 |
| 入组时间 | 卖家首次进入符合条件的定价流程，在展示建议前入组 |
| 主指标候选 | 入组卖家在规定窗口的净成交价值，或预定义挂牌群体在期限内的售出比例；选择一个正式主指标 |
| 诊断指标 | 建议采纳率、完成挂牌率、改价行为、成交价格及售出时间 |
| 护栏 | 卖家收益、退款取消、投诉、预测失败率及延迟 |

不能只比较“采纳建议的人”，因为采纳本身受实验影响；也不能只比较已售出挂牌的平均售出时间，忽略尚未售出的挂牌。应对预定义群体估计效果，处理尚未成交的右删失，并明确指标的分母和入组边界。

票务市场有共享库存、竞争价格和买卖双方相互影响：B 组的售出或定价可能影响 A 组。若干扰明显，简单用户或卖家随机结果可能无法代表全量上线效果，需要评估活动/市场级聚类随机，或有清洗期及时间效应控制的 switchback 设计。聚类实验的样本量和标准误必须按聚类结构计算。

## 8. 数据平台与工具具体负责什么

**分流服务实施实验；Airflow、Dataflow 和 BigQuery 处理及分析实验数据，它们不替代随机化和实验设计。**

| 环节 | 负责组件 | 记录或结果 |
|---|---|---|
| 稳定分配与模型路由 | 业务后端 / 实验服务 | 实验 ID、配置版本、随机单位、组别、入组时间 |
| 实际曝光与互动 | 应用埋点 | 展示内容、位置、模型版本、事件 ID 与时间 |
| 实时清洗与可选监控 | 如已部署，可用 Pub/Sub + Dataflow | 去重的行为明细、延迟及异常监控 |
| 成交、退款和取消 | 业务数据库同步链路 | 权威交易事实 |
| 日常实验数据准备 | Airflow 编排 BigQuery SQL | 分配、曝光与结果关联，按随机单位汇总 |
| 统计分析与报告 | 分析程序执行，Airflow 可编排 | 效应、置信区间、p 值、护栏和质量检查 |

是否已部署埋点与 Dataflow 尚待确认；实验也可以通过批量日志和 BigQuery 分析，不要求实时窗口。

检查实验资格、分组稳定性、事件重复缺失、标签延迟，以及预期与实际分配人数的 SRM。SRM 应优先在预定义分配群体检查；曝光人数不同可能既有日志问题，也有处理导致的展示差异，不能混为一谈。发现质量异常先排查，不应把失真的业务差异解释成模型效果。参考 [Microsoft 关于 SRM 的说明](https://www.microsoft.com/en-us/research/articles/diagnosing-sample-ratio-mismatch-in-a-b-testing/)。

## 9. 常见挑战与实验决策

模型需历史行为时，应明确冷启动用户的策略，并记录特征覆盖。实验期间更新模型、共享训练数据或改变特征会改变处理内容，必须纳入实验方案；不能一边实验一边不记录地替换候选模型。

短期 CTR 和长期留存可能方向不同，长期结论需等待相应窗口，不能用几天的实验宣称改善 30 天留存。新鲜感、周末效应、活动类型和市场变化也限制结论的适用范围。

Multi-Armed Bandit 会随反馈改变流量，Contextual Bandit 还依上下文选择策略；它们是自适应策略方法，不是普通固定分流 A/B 的直接替换。若目标是因果评估，需要相应记录、探索机制和统计方法，不能沿用简单两组比例检验。

最终报告应写明：实验改了什么、谁参与、随机单位、起止及观察窗口、数据质量、主指标差值和区间、护栏、限制与上线决定。只有数据可信、效果满足预设业务标准且风险可接受时才放量；不显著表示证据不足，不自动等于两方案相同。
